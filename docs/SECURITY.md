# Security and operations

- SSR clients use Supabase cookies and `getUser()` for server authorization. The Next.js proxy refreshes verified JWT claims, forwards the SDK’s Cache-Control/Expires/Pragma headers with every cookie batch, and applies private no-store caching even without a refresh. A new SSR client is created per request. Every CRM Server Action independently verifies active staff membership; configuration and team actions require administrator membership. New Auth profiles always receive `visitor`, regardless of user metadata. The database also prevents self access changes.
- RLS covers every application table. Migration 005 also explicitly revokes PUBLIC/anon/authenticated table grants before assigning only needed operations; TRUNCATE/TRIGGER/REFERENCES and audit-sequence access are excluded because normal row policies do not protect those operations. Existing Auth users receive visitor profiles without trusting metadata role claims. Only published properties and their public photos are anonymous-readable. Favorites are user-scoped. Leads, inquiries, internal notes, tasks, messages, profiles, audit records and configuration are private. Server-only public write RPCs are revoked from `anon` and `authenticated`; the service role is used only after origin, validation, ownership and abuse checks.
- Public capture transactions normalize email and deduplicate leads, append inquiries, preserve previous personal details, store each incoming contact snapshot, and make request UUIDs idempotent. A request never accepts a client-selected lead ID. Conversation association requires the hashed HttpOnly visitor cookie. Email ownership is not proved by an inquiry: staff must verify changes to an existing identity.
- Chat ownership is a random 256-bit HttpOnly SameSite cookie, hashed in the database. LocalStorage holds only a non-secret conversation UUID. Public transcript reads require both. Polling returns only that visitor's messages; staff notes never enter the public response. Clearing the cookie loses access to that browser conversation. Anonymous chats are not automatically shared across devices.
- Chat writes use a per-conversation processing lease and revision. Handoff/resolution/assignment/resume changes the revision. A late Gemini response is saved only if status remains `bot` and revision still matches. Staff replies lock the conversation and require `human`. Only authorized staff can resume bot handling. Server-generated copy renders Gemini-selected stored facts; arbitrary generated property claims are never displayed. Selected records are re-read as published after generation. Explicit human requests switch status before invoking the model. SDK automatic retries are disabled to bound latency and cost; the optional explicit fallback never retries authentication or quota errors.
- Uploads require staff, genuine JPEG/PNG/WebP signatures, matching MIME, a random filename, a property-specific path, and bucket MIME/size policies. The Server Action body limit is 12 MB total; each file limit is 10 MB. SVG uploads are rejected. The public photo bucket must contain no confidential files. Unpublishing a listing does not revoke already-public image URLs; remove sensitive images from Storage if necessary.
- Audit records are written by database triggers and cannot be created, changed or removed by application users. They record actor, table, operation, record ID and changed field names, avoiding copies of messages/contact data. The database owner can still manage data under an administrative retention policy.
- Configure `NEXT_PUBLIC_SITE_URL` to the exact canonical origin. Public writes reject all other origins. Next.js also checks Server Action origins. The SQL rate limiter is atomic across instances, salted, and fails closed without server configuration. On Vercel it uses `x-vercel-forwarded-for`; elsewhere the ingress must strip inbound `x-real-ip` and replace it with a trusted client IP. Unknown IPs share a conservative global quota. Email/visitor quotas add a second boundary. Configure ingress request/body limits and an edge limiter to reject oversized JSON before application parsing; the application also checks payload length and Zod field limits.
- Clean old `rate_limits` rows periodically (e.g. delete rows with `window_start < now()-interval '7 days'`), according to operational requirements. Apply a business retention policy for contact data. Use managed backups, monitor Gemini quotas and Supabase errors, and verify restore procedures before launch.
- Fonts load from Google Fonts with local fallback fonts. No advertising analytics or optional cookie tracking is installed. Privacy/terms copy, testimonials, broker credentials, journal content and historical listing records require the business owner's review before publication. Outbound email, SMS and calendar booking are not implemented or claimed; requests are persisted for staff follow-up.

## Database test boundary

`tests/database/bootstrap.sql` supplies minimal Auth/Storage contracts for isolated PostgreSQL policy testing; it is **not** a production migration and must never be applied to Supabase. The SQL suite executes real PostgreSQL RLS and transactional functions, but does not run GoTrue, PostgREST or the Storage HTTP service. Run the credential-dependent acceptance checks in README against your actual Supabase project before launch.

CSV exports verify staff on the server and enforce RLS through the request-scoped client, preserve lead filters, disable caching and neutralize spreadsheet formula prefixes. Destructive controls require confirmation and verify an actual row changed. Authenticated CRM mutations never use service credentials.
